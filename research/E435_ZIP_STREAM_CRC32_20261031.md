# E435 | Bounded streamed ZIP CRC32 corruption control (2026-10-31)

## Falsifiable question

Can the E434 byte-bounded ZIP reader return an apparently valid extension analysis from an archive whose central-directory CRC32 disagrees with its decompressed manifest or JavaScript bytes?

## Baseline reproduction (expected red)

Using JSZip 3.10.1, construct a small DEFLATE archive with a valid manifest, then flip one bit in the central-directory CRC32 field without altering compressed data. `JSZip.loadAsync(bytes)` and the exact pre-E435 `readBoundedZipText` accepted the manifest. `JSZip.loadAsync(bytes, { checkCRC32: true })` rejected it, but that option eagerly decompresses all members and would undermine E434's per-member inflation bounds.

The pre-E435 helper file was copied byte-for-byte from GitHub blob `7b5281c0356a34b912d2c97650b990dbfbd3b751`, verified with `git hash-object`. This demonstrates a **synthetic malformed-archive acceptance defect**, not an observed attack or evidence that CRC32 authenticates an extension.

## Bounded correction

- Compute incremental IEEE CRC32 over each already-bounded streamed `uint8array` chunk.
- Compare the computed unsigned CRC against the central-directory CRC exposed by the loaded JSZip 3.10.x member at the end of that member's stream; reject mismatches before returning text.
- Keep E434's per-entry/shared byte ceilings and fail before allocating the complete decompressed member when the limit is exceeded.
- Reject nonempty loaded members without a verifiable CRC value. JSZip's special representation for a zero-byte loaded member lacks accessible central-directory CRC metadata, so an empty member is still accepted.
- Never call eager `loadAsync({ checkCRC32: true })` or execute archive JavaScript.

## Offline validation and negative results

Node 22.16.0, JSZip 3.10.1, TypeScript 5.8.3, local exact-source harness:

1. **Expected red:** pre-E435 bounded helper accepted the deliberately corrupted manifest CRC.
2. **After change:** 7/7 `node --experimental-strip-types --test regression.test.mjs` controls passed: valid manifest, empty member, multibyte UTF-8, corrupt manifest CRC, corrupt JS CRC, 2 MB compressed inflation bomb, and invalid UTF-8.
3. Standalone strict TypeScript compilation passed: `tsc --noEmit --strict --target es2022 --module nodenext --moduleResolution nodenext zip-bounds.ts`.
4. The modified helper's local Git blob SHA `9665d3e6e5ebd8602dac67347e1b24b7fb250549` matches the committed GitHub blob.
5. **Preserved negative limitation:** an empty ZIP member with deliberately corrupted central-directory CRC still returns an empty string because JSZip discards the CRC metadata for zero-byte loaded members. This is not fully solved.
6. The seven new repository Vitest regression cases were committed, but the full repository Vitest suite, Next.js build and exact-head GitHub Actions have **NOT** been executed for E435.

## Claim boundaries

CRC32 detects some accidental or adversarial corruption but is **not** cryptographic authentication: an attacker can modify data and recompute CRC32. The implementation uses JSZip internal APIs (`internalStream`, `_data.crc32`) and is version-sensitive. It does not prove resistance to malicious ZIP parsing, overlapping entries, duplicate names, crafted metadata, memory-exhaustion attacks, or corrupt empty-member CRC. The 104,857,600-byte bounded-inflation stress result already documented on E434 PR #36 remains a separate synthetic experiment, not a formal resource bound.
